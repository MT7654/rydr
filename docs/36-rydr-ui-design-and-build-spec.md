# Rydr UI design and implementation specification

14 October 2026 · proposed redesign · implementation has not started

Read with [research and current UI audit](35-ui-research-and-review.md), [custom Mobbin MCP references](35-mobbin-mcp-reference-appendix.md) and [dataset/policy update](34-new-supplied-datasets-and-policy.md).

The [component research and decisions supplement](36-component-research-and-decisions.md) adds six inspected Mobbin references and the final component-level selection/state matrix. Its upload, monetary-validation and explicit-action-label refinements apply to this specification.

## 1. Outcome and scope

Rydr should feel like a purpose-built ride resolution product. The interface should explain each case through its decisive records and uncertainties, keep the current task obvious, and give every role one connected journey. The required outcome is not more visual decoration on the existing cards. It is a new information hierarchy that makes the same working features easier to use.

The default reviewer surface is an evidence desk. The default rider/driver surface is a ride overview and resolution receipt. Both use existing domain state, permissions, version checks, task selection, live agents and ledger services. Do not replace business logic or add a second client-owned workflow.

In scope: navigation and page hierarchy; worklist/ride list; case exhibits; stable agent monitoring; contextual source/assistant panel; decision/appeal form presentation; evidence-response presentation; outcome/history; responsive and accessibility states; original conceptual art. Existing secondary features remain reachable in context or under Team tools/Help.

Out of scope: new auth service, real external payments, notifications, account suspension, new model provider, additional ADP agents, changing policy precedence, invented data, new analytics claims, recording a submission video. Do not seed everyone into a pre-settled case to make the visuals look complete.

## 2. Non-negotiable invariants

| ID | Requirement |
| --- | --- |
| INV-01 | Preserve server role gates and party filtering. Hidden controls do not replace permissions. Driver/rider cannot enter reviewer-only actions through URLs, forms or Navigator. |
| INV-02 | Keep business status, selected task, displayed historical run and effective decision as separate dimensions. A refund can coexist with an open appeal; an older run can coexist with a newer case version. |
| INV-03 | Reuse `WorkspaceView.primaryAction`, secondary actions and expected revisions. No UI component invents an allowed action from a local status string. |
| INV-04 | Historical views use frozen evidence, policy, findings and agent outputs. They are read-only and clearly identify the displayed version. Sources are fetched using the displayed run context. |
| INV-05 | No amount, liability, source-authenticity verdict or policy choice is generated by UI copy or a decorative image. Calculated eligibility is not an awarded amount. |
| INV-06 | Keep actual and fixture assessments visibly distinguishable. Never silently substitute sample outputs on live failure. Show simulated source calls and financial effects in their relevant contexts. |
| INV-07 | Written statements do not silently become verified records. Evidence-acceptance actions remain conditional in the client and validated in the server. |
| INV-08 | Appeals from either party create/retain the real reviewer task and reasoned resolution. Reviewing an appeal is distinct from auditing an existing decision. |
| INV-09 | Driver credit and rider recovery are separate. A failed recovery must not reverse an already approved driver credit merely to simplify the display. |
| INV-10 | Opening an inspector, resizing the layout or changing a view must not trigger an ADP call. Summaries use existing structured findings. Navigator runs only on explicit submission. |
| INV-11 | Session role switch preserves the session; fresh-session control changes namespace using the existing mechanism. DISP-002 is open in a fresh session. Explain sample identities and eventual production login in Session controls. |
| INV-12 | Exact complaints and full agent outputs remain readable. No sentence is clipped by fixed height, overflow hidden, ellipsis or a line clamp in the source/agent detail view. |

## 3. Information architecture

### Application shell

Reviewer: primary navigation is **Worklist**. Lower-level **Team tools** retains intake, policy library, precedent curation, operations and payments/recovery management. Their contextual entry points are also available from a case. No general feature directory is inserted before the worklist.

Rider/driver: primary navigation is **My rides**. Policies and help are supporting links. Preventing a pickup dispute appears on the relevant ride/pickup view; payments and appeal controls appear inside the relevant outcome. Do not expose Add case/intake, review queue, operations or precedent curation.

Session controls is a visually separate utility at the bottom of the rail or the mobile account menu. Required description: “Role switching is available for this demonstration using shared sample identities. The production product would use login and role-based access.” Fresh session description explains that it opens a clean sample workspace. Do not imply the current role selector verifies identity.

### Reviewer case destinations

Show three destinations: **Review**, **Outcome**, **Record**. Review contains the brief, findings, source exploration and current-task form in one working surface. Brief, assessment, evidence and decision remain canonical backend sections and deep-link targets; visually group them rather than removing support for existing URLs.

Provide a compact in-page index within Review when useful: Overview, Findings, Evidence, Current task. This is not another horizontal row of large tabs. Opening a task or source scrolls/focuses the appropriate region without losing orientation. Automatic stage choice remains derived from the server. Clicking Outcome deliberately selects outcome; returning to a pending task selects Review and the task form.

Mapping: `brief`, `assessment`, `evidence`, `decision` -> Review; `appeal` -> Review/current appeal task; `outcome` -> Outcome; `history` -> Record. Preserve `task`, `run` and `mode` parameters, except when explicitly returning from a historical snapshot to the current case. Browser back must restore selected source and scroll where practical. Invalid/stale task links retain existing safe handling.

Party case destinations: **Your ride** and **Record**. Your ride presents the open task or outcome automatically; evidence/request and appeal forms are contextual subviews with a Back to your ride control. Keep existing section URLs as aliases. No empty “Decision” tab appears for a party.

## 4. Layout geometry and responsive behavior

Use CSS grid with minimum canvas widths, not three fixed columns forced into every viewport. Global rail default is 104px wide with visible labels, brand and utility. Expanded rail is 200px, explicitly chosen and remembered per role; it should not silently take priority over the case canvas. Reviewer case list is 248px when open. Context inspector is 360px, resizable 320–440px on a sufficiently wide desktop; resizing is optional for initial release. Main canvas needs approximately 680px usable content plus 48px padding.

| Viewport | Required behavior |
| --- | --- |
| ≥1600px | Rail + optional 248px case list + main canvas + optional 360px inspector can fit. Never open both optional panels by default simply because space exists. |
| 1280–1599px | Default rail + list + canvas. Opening inspector automatically closes list if canvas would fall below 728px including padding. A labelled Cases control restores it and closes inspector if necessary. |
| 1024–1279px | Rail + canvas; list opens as a popover/sheet. Inspector is side panel only when minimum canvas width fits; otherwise modal sheet. |
| 768–1023px | Compact top shell, single canvas; Sources/Navigator opens an accessible sheet. Case selection is a labelled button. |
| 320–767px | Single column, 16–20px gutters, top ride/case identity, one current task. Source and task sheets use full width. Exhibits become vertical lists with text equivalents. |

Decision forms must remain usable at 200% zoom. At 400%, apply narrow layout/reflow rather than squeezing columns. A sticky action footer adds matching content padding, respects safe areas and cannot cover validation text, citation buttons or the last input. Avoid nested scrolling in ordinary short case content; inspector may scroll independently. Preserve focus when switching between inline and sheet layouts at a breakpoint.

Desktop reviewer hierarchy: compact case header; current state/action strip; category exhibit; decisive findings; current task; contextual supporting records. Initial assessment screen shows brief/exhibit and the assessment action in this same canvas. No blank summary placeholders occupy a full screen.

## 6. Reviewer worklist

Top: title, short subtitle “Choose a case to assess or resolve”, search and Add case secondary action. One compact summary line includes cases needing decisions and waiting requests only when present. SLA method and sample data explanation move into a labelled information disclosure; visible lateness/priority remains on affected rows.

Filters retain All, Needs assessment, Needs decision, Waiting for evidence, Appeals, Payment attention and Closed. Keep URL-backed filters and exact counts. “All” remains the fresh-session default. Compact zero-count filters may live in More at narrow widths, but must remain keyboard reachable and labelled.

Desktop five columns: **Case / Next step / Amount / Owner and target / Open**. Case cell contains unbroken ID, issue and provenance/version as subdued second line. Next step combines status and task without repeating “No assessment yet” plus “Run assessment” in three places. Amount is right aligned. Owner/target shows actual next actor and target if any. Action says Open case; do not start a paid run from row selection.

At <900px, use accessible list rows: case/issue, amount, next step, target and Open. No horizontal overflow for case IDs or actions. Filter text wraps or uses a labelled filter sheet, not truncated invisible chips. Empty state explains the selected filter and offers Clear filter; only a truly empty case collection uses decorative empty art. Preserve multi-task indicators and choose the server's selected task when opening.

## 7. Reviewer review canvas

### Header and current task

Header: breadcrumb Worklist /case ID, human-readable issue, disputed amount, case version/provenance, current business state. Separate current-task label when an appeal or evidence request overlaps with the business state. One current-task button; selecting it focuses the relevant form. The form's own submission button remains the concrete action. Do not render a duplicate filled CTA in the assistant panel.

State strip names what is happening and who acts next. Examples: “Ready to assess ·Reviewer”, “Assessment running ·Agents”, “GPS accuracy requested ·Driver”, “Appeal ready ·Reviewer”, “Decision recorded ·Payment pending”. These strings map server data; the UI must not infer a final state from the presence of an amount.

Compact process context can show received/assessed/decided/outcome as text. Prior to a run, additional-evidence stage says “Not requested yet”. Only established unnecessary steps say “Not needed for this decision”. Do not use a universal five-step wizard that falsely implies all cases require a human decision.

### Case exhibits

`CaseExhibit` renders actual category records and deterministic SVG/HTML. Its inputs are the existing record, evaluation and governing pack, not a new LLM output. It has readable text/table equivalents and source controls.

| Category | Required exhibit | Missing/conflicting state |
| --- | --- | --- |
| No-show | Parallel clocks: scheduled pickup, reported arrival, timer event, cancellation; message/call markers; threshold labels beside each source. | DISP-002 shows supplied policy five-minute rule and embedded eight-minute rule separately. GPS accuracy absent -> Unknown; no exact physical pickup-zone circle or map confidence. |
| Route | Recommended/actual distance on one scale; excess distance; notification and traffic records; eligible amount and reviewer limit. | DISP-001:20.5km/24.8km/+4.3km;S$3.44 eligibility; greater-than2km requires human decision. Traffic justification and notice are separate conditions. |
| Fare | Quote vs final fare bridge: unchanged fixed portion and attributable surge delta; notice state; inspect pricing log. | DISP-003:S$12.00 quote/S$16.50 charged/S$4.50 disputed delta;S$9 surgeable base/S$3 fixed;no pre-pickup notice recorded. If records do not reconcile, label gap; don't force the bridge to balance. |
| Damage | Uploaded source image viewer, visible-condition observations, receipt/quote and trip-context rows. | Capture time, trip linkage and origin can each be Unknown. Valid but untrusted C2PA is distinct from trusted provenance. Synthetic imagery is labelled. Pixels do not prove who caused damage. |

Numbers are formatted from cents/distances/timestamps; never hard-code supplied examples into reusable components. Route displays a distance comparison by default, not an invented map. A schematic ride ribbon may show recorded origin/destination without spatial claims; label “Trip summary” rather than “GPS route”.

### Decisive findings

Use three groups: **Supported by records**, **Still unresolved**, **Party accounts**. Counts and visible content depend on actual findings. Show highest-priority material questions first; include a See all findings control for remaining material/nonmaterial records. Each row includes question, short finding text, kind, one-line implication and source links. If no concise structured implication exists, show the existing finding intact; do not manufacture one by extracting a confident first clause from contradictory prose.

A compact overview may feature three to five material findings, chosen by a deterministic documented ordering. It is not an arbitrary truncation of the first three entries. All material blockers appear in the review task and cannot be hidden solely by the overview cap. Claims cannot be styled as recorded observations.

Two opposing statements appear as two labelled accounts with exact text accessible via Read full account. Opening full text occurs in the inspector, preserving paragraphs, all characters and source attribution. Do not show an ellipsis as the only way to access the complete complaint.

## 8. Agents and assessment progress

Replace long three-column essays with one stable **Assessment team** strip and a **Findings comparison**. The strip stays above the exhibit and findings throughout the live run and terminal states; new results fill regions below without remounting the strip elsewhere. Reserve approximate64–92px height, adapt to stacked rows on mobile; do not reserve essay-card heights.

Core lanes: Rider advocate, Driver advocate, Judge. Supplemental collection/image/risk/policy work is shown as a compact preparation detail when actually recorded; not displayed as extra independent agent deployments unless that is true. Stage labels derive from actual run/call events. The judge waits until advocates are validated. “Waiting”, “Working”, “Completed”, “Unavailable” have distinct text/icon states. No fabricated progress percentage or completion time.

At terminal state, lead with the judge's actual disposition: supported amount/recommendation, or “Human decision needed ·No automatic amount awarded”. List material blockers below. The actual final reason is available in Full judge assessment. Collection planner's reason and risk prose move into relevant evidence/integrity context; broad methodology moves to Help.

Comparison is finding-based, retaining the semantics of `AgentComparison`: Uses in case, Acknowledges contradiction, Uses and challenges, Not cited; Judge Established/Disputed/Not selected. Absence of citation never becomes agreement. On mobile each finding stacks its three agent positions. On desktop column widths are balanced but content height is naturally variable. Selecting an agent opens its complete output, cited evidence and safe execution summary in the inspector. Do not expose hidden chain-of-thought.

Terminal refresh retains selected inspector, task, context and scroll. Polling stops at terminal state. On disconnected polling, show recorded progress, uncertainty about the latest state, and Reload status. Provider failure gives a bounded safe error, Retry when allowed, and human path when allowed. Technical request IDs/events remain in Record/technical details; secrets never render. Call counts remain inspectable for judging.

## 9. One contextual inspector

Inspector modes: **Source**, **Policy**, **Agent**, **Navigator**, **Record details**. Only one inspector mounted open at once. Header includes mode/title, version/run context and Close. Selected source link is visibly active in the main canvas. Escape closes and returns focus to the trigger. Narrow view uses a modal dialog/sheet with focus containment; desktop panel uses complementary landmark and logical focus movement.

Source display: human label, original record ID via Details, type, submitting/source actor, time/timezone, provenance, fields/full original text, limitations, relevant linked findings. GPS details include time, party, lat/lon if available, recorded accuracy or “Not supplied”. If a metadata field is absent, use an explicit Unknown/Not supplied label, never zero or blank. Sensitive fields obey existing role filtering.

Policy display: pack/version, source authority, effective date, exact relevant clause, current finding reference and source link. Clearly distinguish organizer-supplied reference from public website snapshot and old embedded examples. A conflict can pin two labelled clauses within the inspector; selecting one does not establish precedence. Page-level policy library remains available under supporting tools.

Navigator: contextual suggestions for selected task/findings; retains existing provider readiness and case/task/revision/run context. “Ask about this case” opens it. Its response can link to records or prepare a draft through existing allowlisted mechanisms; it cannot secretly submit anything. New task/version resets incompatible suggestions and stale context. Do not auto-send a suggested question on opening. Repeated clicks while one request is pending cannot generate duplicate calls. Current failure/unavailable state names optional assistance; task completion remains available without it.

## 10. Evidence request and response

Show an evidence request as a task conversation, not a chat service: what is requested, why it matters, who responds, current state, the response and its evidence type. An unfulfilled request has a clear next actor; submitted responses have Review response for reviewers.

Party submission progressively exposes the correct form for written statement, GPS accuracy correction, supplied record or other existing supported response type. GPS record selection includes readable timestamp/role/accuracy and an Inspect record control before selection. Selection state is separate from opening details. Both riders and drivers can inspect the records they are allowed to see; no raw-ID checklist without context.

Reviewer response presentation separates the statement from attached structured records. “Accept evidence into a new version” is enabled only when the existing domain validation permits it. Otherwise show disabled control and persistent explanation: “Statement recorded. No structured evidence to add.” The reason is visible without hovering. Request clarification/record decision appears only when allowed by authoritative actions.

Acceptance confirms the resulting version, changes and need for reassessment. Reassessment stays an explicit allowed action. On a stale case/task revision, show conflict explanation and reload path while retaining the user's draft locally where safe; no silent overwrites. Never re-accept the same response or post duplicate evidence. Server-side rejection remains necessary even with correct disabled styling.

## 11. Decision and appeal review

Current-task header states Human decision, Appeal review or Audit; don't mix them. Decision form shows outcome choices supported by the domain, applicable amount field, concise financial preview, reason and selected supporting sources. Required reason is a plain-text record; preserve original text/line breaks. Minimum length remains the existing rule; UI explains it without inventing a new policy.

If Judge abstained/human_review: one reason field labelled “Why this outcome is supported”. No mandatory override reason. If a human departs from a concrete automatic recommendation, show the existing explicit departure reason as applicable. The form explains the recommendation and actual proposed change, rather than throwing an unexplained error at submit.

Review draft state includes case/version, selected task/revision, decision, amount, main reason and financial effect. One final Record decision action calls the existing mutation. Back to edit keeps values. Clear cases that auto-settle do not gain an unnecessary mandatory human approval step.

Appeal review includes appellant, original decision/amount/version, exact grounds, new records and current-case differences. Options labelled Accept appeal /Reject appeal use existing semantics. A reason is required for both. Accepting an appeal must show what actually changes; do not imply every acceptance guarantees a full refund. Rejecting records the reason and preserves the effective decision as the domain requires. Appeal state remains visible in Outcome until resolved, for both appellant roles. Reviewer audit stays secondary and cannot replace an open appeal task.

Submission pending state prevents duplicate clicks. On success, focus a labelled confirmation and offer View outcome; state/queue refresh reflects the server. On failure, retain values and focus the error summary with field-specific links. After settlement, human decision text remains ink-coloured and readable; it must not inherit muted or disabled button styling.

## 12. Party ride story and outcome receipt

My rides lists ride identity, issue, exact disputed amount and next requested action/status. Dates/recorded journey endpoints provide recognition. Do not invent vehicle images/portraits. A small category glyph or decorative shared illustration is acceptable when clearly unrelated to evidence.

Your ride starts with recorded route/date and case identity, then one current message: awaiting assessment, evidence requested, outcome recorded, or appeal pending. An evidence response or appeal is an explicit current task. The user does not need to choose among four nearly equivalent feature tabs to continue.

Outcome order: exact effective outcome and amount; recorded reason; key questions/findings; financial status; available next action; case record. Party-specific wording should explain the effect (“S$4.50 refund approved”) and whether a simulated ledger entry has posted. Never write “Paid” simply because a decision has been recorded. Full policy/source explanation is one contextual selection away.

Use supported/unresolved question rows inspired by the inspected Lyft result, but avoid “We didn't find” when evidence is simply missing. Instead say “Not established” or “Still unresolved” based on findings. Do not use generic Yes/No satisfaction controls as the appeal process. Appeal CTA opens the real form; after submission, show grounds and reviewer status; after decision, show the recorded reason and changed/unchanged amount.

Financial tracks are independent:

- Rider refund: approved ->simulated posting pending/posted/failed as recorded.
- Driver relief: reviewer approval ->simulated driver credit pending/posted/failed as recorded.
- Rider recovery: requested/pending/failed/succeeded as recorded; preserve restrictions on party-visible information.

Show only actual events, not all possible future stages as already achieved. A failed recovery adds an explanation beside the driver credit that it remains recorded when that is true. Ledger technical IDs are supporting details. No bank transfer/logo appears without an actual integration.

Pickup prevention remains on the ride/pickup subview: suggested meeting point/instructions, rider/driver acknowledgement and receipt of relevant notice using existing services. The generated curb illustration decorates the introduction, never claims actual location. Contextual navigation returns to the same role/ride; it does not promote prevention into a separate top-level product.

## 13. Record and audit

Timeline groups events by case date and type: complaint, source acquired, evidence version created, assessment recorded, human decision, appeal submitted/resolved, financial posting. Each has actor, time, concise description and detail link. Assessment events link to the frozen run. Version events link to the precise changes; full source JSON remains in technical details/export where authorised.

Case chronology is distinct from the trip-event exhibit. Do not mix GPS arrival events with “human decision recorded” into one unexplained long list. A recorded-run banner stays above historical content and offers Return to current case; no current mutation button remains enabled. Policy/finding citations resolve against that snapshot.

## 17. Delivery phases and gates

### Phase A — structure and semantics (P0)

Consolidate design tokens and conflicting stylesheet overrides; fix all colour-state inheritance. Build the shell, responsive worklist, case header and review grouping. Move Navigator into inspector. Keep routes and API behavior. Add component variants and source focus behavior. Gate: no source/task/version loss during navigation; normal text/hover readable; current task visible at desktop and mobile.

### Phase B — evidence and agents (P0/P1)

Build category exhibits and typed finding rows. Refactor RunMonitor presentation while retaining polling/call records. Preserve complete agent output and source context. Replace repetitive static teaching panels with contextual preparation records. Gate: live run never relocates assessment strip; unknown and conflict states remain explicit; exact supplied arithmetic unchanged.

### Phase C — task completion (P1)

Refine evidence requests/acceptance, human decision/appeal draft review, outcome receipt and financial tracks. Integrate corresponding party views and history. Gate: both-party appeal loop works, statement acceptance stays disabled, human abstention asks one relevant reason, no duplicate posting or effect change.

### Phase D — visual polish and validation (P2)

Integrate conceptual art into relevant intro/prevention views; improve empty/error/loading states and small-screen composition. Record screenshots of acceptance scenarios, compare current/proposed task usability, remove dead CSS only after references checked. Do not hold functional completion for optional additional images.

Build behind a development-only presentation flag if helpful; do not add a public redesign toggle to the demo path. Preserve fallback styling during implementation until new surfaces pass; remove duplicated visual hierarchies before release. No schema migration or new ADP key should be needed for this UI scope.

## 19. Review criteria before choosing the final visual direction

Reviewer: identify disputed amount, governing policy, main unresolved fact and next actor within ten seconds; inspect the first supporting source in one selection. Party: identify the exact decision, its financial status and its available next action without scrolling past methodology. Source detail: no lost task/draft. Every category must have a meaningful visual exhibit, not a copied generic box grid.

Use the local concept preview to assess hierarchy and image fit, not to approve fabricated functionality. If screen testing shows the user still has to read multiple introductory paragraphs before finding the decisive fact, rework that surface before implementing additional illustrations.
